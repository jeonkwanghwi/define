# 마을 (tab2) v1 — 설계

> 2026-09-20. 브레인스토밍 결과. 기획 맥락: [PLANNING.md](../../PLANNING.md) §4 tab2 · 개발 맥락: [DEVELOPMENT.md](../../DEVELOPMENT.md) §6 "탭2 마을".

## 무엇을 만드는가

이웃(다른 사용자)의 집이 있는 마을을 아바타로 **길을 따라 거닐다가**, 집을 누르면 **그 사람의 정의**를 보는 화면. 광장이 "단어 → 사람"이면 마을은 "사람 → 단어".

## v1 범위 (확정)

**포함**
- 배경 그림 1장 위를 아바타가 **길 따라** 걷기
- 맵 5개 — 중앙 + 동(봄)·남(여름)·서(가을)·북(겨울). 가장자리로 걸어가면 옆 맵으로 전환
- 집 탭 → 문 앞까지 걸어감 → 하단 시트로 그 사람의 닉네임 + 정의 목록
- 새로고침 → 집 주인(이웃) 재배치
- 가입 필요 탭(기존 `AuthGate` 유지)

**제외 (후속)**
- 내 집 짓기·꾸미기, 건물 설치 시간, 잉크 소비
- 나이·성별·관심사 필터 (프로필 데이터는 이미 서버에 있으나 v1에선 안 씀)
- 메모 기반 AI 이미지 생성 (6/28 회의 결정 — v2로 미룸. 프리셋 배경 먼저)
- 방명록·쪽지, 실시간 요소 일절

## 핵심 결정과 이유

| 결정 | 이유 |
|------|------|
| **배경은 통짜 그림 1장** (타일 조립 X) | 조각을 이어붙이면 이음매·스타일 불일치가 생긴다. 한 장이면 톤이 통째로 일관되고, 그림 교체가 파일 하나 바꾸기다. AI 이미지도 "한 장"은 잘 뽑는다(타일은 못 뽑음 — 2026-06-20 결론). |
| **길은 이미지가 아니라 좌표 데이터** | 이미지 픽셀을 읽어 걷기 가능 영역을 판정하는 방식은 RN에서 비싸고 까다롭다. 길을 노드+간선 그래프로 따로 두면 가볍고 결정적이며, 배경을 갈아도 좌표만 맞추면 된다. |
| **집은 배경에 그려져 있고, 우리는 "문 앞 좌표"만 가짐** | 집 스프라이트를 배경 위에 얹으면 그림체가 어긋날 위험이 크다. 배경에 그려진 집을 슬롯으로 취급하면 아트가 항상 일관된다. 대신 **맵당 집 수는 그림이 정한다**. |
| **맵 데이터는 앱에, 이웃만 서버에서** | 배경 이미지가 앱 번들에 들어가므로 좌표도 앱에 있는 게 자연스럽다. 서버는 "누구를 넣을지"만 정한다. |
| **슬롯이 사람보다 많으면 중복 배치** | 초기 가입자가 슬롯 수(약 30)보다 적다. 빈집투성이 마을보다 같은 사람이 두 동네에 있는 편이 낫고, 사람이 늘면 중복은 자연히 사라진다. 코드가 "사람이 충분하다"는 가정에 기대지 않게 하는 안전장치이기도 하다. |
| **집 입장 = 하단 시트** (별도 실내 화면 X) | 실내 배경 그림이 5장 더 필요해지고, 마을로 돌아오는 맛이 끊긴다. 꾸미기가 들어오는 v2에 재검토. |

## 데이터 구조 (프론트)

`src/data/village-zones.ts` — 맵 5개의 정적 정의. 좌표는 전부 **0~1 비율**(기존 `village-mock.ts` 규칙 유지)이라 해상도·기기와 무관하다.

```ts
type ZoneId = 'center' | 'east' | 'south' | 'west' | 'north';

type Zone = {
  id: ZoneId;
  season: '중앙' | '봄' | '여름' | '가을' | '겨울';
  background: ImageSourcePropType;   // require('assets/village/bg-*.png')
  nodes: Record<string, { x: number; y: number }>;  // 길 위의 점
  edges: [string, string][];                        // 이어진 길
  slots: { id: string; door: string; label?: string }[];  // 집 문 앞 = 길 노드 id
  exits: { dir: 'up'|'down'|'left'|'right'; node: string; to: ZoneId; enterAt: string }[];
};
```

- **걷기**: 탭 지점 → 가장 가까운 간선 위로 투영 → 그래프 최단경로(다익스트라, 노드 수십 개라 비용 무시 가능) → 경로를 따라 순차 애니메이션.
- **집 탭**: 그 슬롯의 `door` 노드까지 걸어간 뒤 시트 오픈.
- **맵 전환**: `exits` 노드에 도착하면 대상 맵으로 페이드 전환 + 아바타를 `enterAt` 노드에 배치(= 들어온 반대편 가장자리).

## 서버 계약 (백엔드 신규 모듈 `village`)

```
GET /api/village/neighbors?count=30        (JwtAuthGuard)
→ { neighbors: [{ id, nickname, words: [{ word, text, savedAt }] }] }
```

- 정의가 1개 이상인 유저 중에서 랜덤 표본. **본인 제외**(남의 집을 보러 가는 공간).
- 유저가 `count`보다 적으면 중복을 허용해 `count`개를 채운다.
- 유저당 정의는 최신 5개까지(시트에서 그 이상은 안 보여줌).
- 신규 테이블 **0개** — 기존 `User`·`Entry` 재사용(광장과 같은 데이터).
- 배치(어느 집에 누가) 는 **클라가** 정한다: 받은 목록을 맵별 슬롯에 순서대로 꽂는다. 새로고침 = 재요청.

## 화면 구성

```
AppHeader (기존 공통)
────────────────────
[계절 이름]        [새로고침]     ← 얇은 한 줄
────────────────────
        배경 그림
        + 아바타
        + (전환 지점 표시)
────────────────────
하단 탭바 (기존)
```

- 세로 고정. 배경은 `cover`로 채우고, 좌표는 실제 렌더 박스 기준으로 환산(레터박스 보정).
- 집 시트 = 기존 `neighbor-sheet.tsx` 확장(닉네임 + 정의 카드 + 스르륵 등장).
- 모션: 걷기는 등속 보간, 맵 전환은 페이드, 시트는 기존 슬라이드 규칙. (PLANNING §2 "부드러움" 상시 원칙)

## 검증 방법

1. **서버 계약(curl)**: 무토큰 401 / 정의 없는 유저 제외 / 본인 제외 / 유저보다 count가 클 때 중복으로 채워 정확히 count개 / 매 호출 순서가 달라짐.
2. **걷기 로직(단위 테스트)**: 최단경로가 길을 벗어나지 않는지, 임의 탭 지점이 항상 길 위로 투영되는지, 경로가 없는 노드쌍이 없는지(그래프 연결성).
3. **맵 전환**: 5개 맵을 한 바퀴 돌아 중앙으로 복귀, 진입 위치가 반대편 가장자리인지.
4. **실화면**: 웹에서 실제로 걸어서 집 진입 → 시트에 서버 데이터가 뜨는지 캡처.

## 알려진 미결

- **아바타 스프라이트** — 배경 그림체(픽셀아트)와 맞는 캐릭터가 필요하다. AI는 투명 배경을 못 뽑으므로 별도 처리 필요. v1은 기존 `char.png`로 시작하고 아트 매칭은 후속.
- **배경 용량** — 장당 2MB대면 5장에 10MB+. 앱 번들에 부담이라 WebP 변환·다운스케일 필요.
- 맵당 집 수는 최종 그림이 확정한다(예시 그림 기준 9채). 슬롯 좌표는 그림을 보고 찍는다.
